# 研究计划：软件代理生命周期中的模型与 reasoning effort 联合路由

## 1 暂定题目

**Joint Model-and-Effort Routing for Long-Horizon Software Agents**

中文可用

**面向长程软件代理的模型层级与推理档位联合路由**

## 2 研究空缺

公开研究已经覆盖

- 不同模型之间的路由
- 单模型不同 reasoning effort 的逐步路由
- reasoning strategy 与模型的联合选择
- 质量和成本预测

仍值得系统量化的交叉点是

- 同一 GPT-5.6 家族内 Sol、Terra、Luna 与 medium、high、xhigh 的联合选择
- 真实软件生命周期阶段，而非只用独立问答题
- 每轮结束后的下一轮建议，而非只在单次输入前分类
- 长上下文、压缩交接包、工具循环和验收器强度的交互
- 用户质量偏好与范围外修改风险的联合效用

该方向不是“没人研究过路由”，而是把已有路由研究推进到真实软件代理、同家族 effort 曲线和连续迭代场景

## 3 核心假设

- H1：最优路线随任务阶段显著变化，不存在稳定的全局默认模型和 effort
- H2：对强验收、低歧义实现，Terra high 与 Sol xhigh 的通过率差距小于它们在开放架构任务上的差距
- H3：压缩交接包对通过率和用量的影响，可能大于 high 到 xhigh 的边际影响
- H4：高 effort 在部分任务上会增加范围漂移或过度思考
- H5：两阶段路由，即先判定任务合同和风险，再选择模型与 effort，优于直接按关键词分类
- H6：预测“是否需要升级”比预测“精确最佳路线”更容易校准

## 4 系统版本

### v0.1 规则路由器

- 硬门
- 三种用户策略
- 一个主推荐和两个备选
- 明确验收、停止和权限边界
- 本地结果日志

### v0.2 校准路由器

- 按任务类别计算通过率区间
- 估计模型与 effort 的交互
- 用最低置信下界选择路线
- 对分布外任务拒绝自动降档

### v0.3 学习路由器

- 使用历史任务嵌入与结构化风险特征
- 输出每个候选路线的质量和用量分布
- 使用上下文 bandit 或离线策略学习更新路由
- 保留规则硬门作为安全约束

## 5 数据结构

每个实验记录至少包含

- 任务模板 ID、仓库和初始 commit
- 任务阶段和结构化风险字段
- 推荐路线和实际路线
- 模型快照、effort、上下文模式和工具权限
- 所有验收结果
- 严重缺陷、范围外修改、回归和过度思考标签
- tokens、工具调用、时延和返工
- 人工覆盖推荐的原因

## 6 里程碑

| 里程碑 | 交付物 | 通过条件 |
| --- | --- | --- |
| M1 | 规则路由器和 15 个单元案例 | 所有硬门和反偏置案例通过 |
| M2 | 30–50 个任务模板 | 每类任务有可复现验收器 |
| M3 | 第一轮随机交叉实验 | high/xhigh 差异有区间估计 |
| M4 | 校准模型 | Brier score 和覆盖率优于规则基线 |
| M5 | 真实项目影子部署 | 没有生产写入冲突，记录完整 |
| M6 | 论文和开放数据 | 任务、脚本、结果和限制可复现 |

## 7 成功标准

研究成功不要求证明低档位总是更好

满足以下任一项即有价值

- 找到明确的 task-class × model × effort 交互
- 证明某些任务上 xhigh 有稳定边际价值
- 证明某些任务上 effort 增加无益或有害
- 提供比静态全局默认更低的严重失败率
- 在不降低验收通过率的情况下显著减少工具循环或返工
- 给出可校准、可拒绝、可审计的下一轮推荐器

## 8 风险

- 模型服务持续更新，快照不可完全冻结
- ChatGPT Credits 与 API token 日志口径不同
- 真实软件任务难以完全复现
- 验收器可能偏向某一实现风格
- 用户覆盖推荐会造成选择偏差
- 高风险任务不能进行低配置影子写入

应通过时间戳、隔离工作树、预注册分析、强验收器和只读影子运行降低这些风险
